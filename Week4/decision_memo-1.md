# Part 10 — The decision memo

## 1. What did you build, and which control caught which failure?

I built a ReAct agent driven by a real language model, with Pydantic schemas, four validation gates, a dispatcher, and a controller loop.

The controls handle different types of failures:

- **Gate 1 — Schema:** checks whether the tool arguments have the correct structure and data types.
- **Gate 2 — Existence:** checks whether identifiers such as `order_id` exist in the known data.
- **Gate 3 — Validity:** checks whether the requested action is valid in the current context.
- **Gate 4 — Coherence:** checks whether a consequential action such as `request_approval` has enough evidence before it can proceed.
- **Controller loop:** controls the maximum number of steps and token budget, detects repeated actions, handles malformed model outputs, and manages escalation or pending approval.

The agent used the model **`Qwen/Qwen2.5-1.5B-Instruct`**.

## 2. Which failure did no control catch, and why not?

The main failure that no control caught was the **unsupported or harmful content in the final answer** in Exercise 3.

The audit result showed:

```text
claim_is_supported: true
```

The important point is that the problem was in the **final natural-language answer**, rather than in a tool call.

Gates 1–4 operate on tool calls and their arguments. They can validate the schema, existence, validity, and coherence of an action, but they do not directly validate whether the final generated answer is fully supported by the evidence in the trace.

Therefore, the four existing gates could allow the problem to pass.

This is why the lab proposes an additional **fifth gate for output validation** that checks whether the final answer is supported by the trace.

## 3. What would you add first, and why that first?

I would add a **fifth gate for final-answer validation** first.

This gate would run after the model generates the final answer but before the answer is delivered to the user.

It would check whether the claims in the final answer are supported by the trace and known evidence.

If the answer is not supported, the system could:

- retry the answer,
- escalate to a human, or
- refuse to provide the unsupported claim.

I would add this first because the existing four gates already provide protection for tool calls, while the final natural-language response remains a gap.

## 4. How often could the model not follow the contract? Quote `REPAIRS`, and say what that implies about running a 1.5B model in production.

The model used in my run was:

```text
Qwen/Qwen2.5-1.5B-Instruct
```

The `REPAIRS` result from my execution was:

```text
fence_or_prose: 11
retries: 6
gave_up: 0
```

Therefore:

- **`fence_or_prose = 11`** → the model failed to follow the required output contract **11 times**.
- **`retries = 6`** → the system attempted repair/retry **6 times**.
- **`gave_up = 0`** → the model did not completely give up.

This gives a **Level-1 baseline of 11 contract-format failures**.

The result shows that a **1.5B model should not be trusted to produce perfectly structured tool calls by itself in production**. It needs schema validation, retries, gates, and controller-level safeguards to handle malformed or non-compliant outputs.

## 5. Where does your agent still trust something it should not?

The agent still trusts the **final answer generated by the language model** more than it should.

The tool calls are protected by the four gates, but the final natural-language answer is not fully protected by those same gates.

Exercise 3 demonstrated this weakness: the audit reported:

```text
claim_is_supported: true
```

but the exercise specifically highlights that the damage can occur in the **final answer rather than in a tool call**.

Therefore, the agent should not completely trust the model-generated final response without an additional output-validation mechanism.

## 6. What did this lab not tell you?

This lab did not tell me how reliably the agent would perform in a real production environment.

There are several important limitations:

1. The model used was **`Qwen/Qwen2.5-1.5B-Instruct`**, which has a different failure profile from a frontier model.
2. The lab uses **greedy decoding**, which makes runs comparable within the session but is not a complete reproducibility plan.
3. Each exercise was run **once**, so there is no estimate of variance across repeated runs.
4. The five customer emails were written by one person, so they represent a **smoke test rather than a comprehensive evaluation set**.
5. Therefore, the observed failures and the `REPAIRS` numbers should not be treated as a complete measurement of how the agent would behave on a larger production workload.
